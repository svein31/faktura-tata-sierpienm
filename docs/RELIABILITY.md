# Verification and operations

`npm run verify` builds the app, checks TypeScript and lint, runs regression tests, then isolated MongoDB HTTP, warehouse concurrency, OCR lease recovery, backup/restore and Chromium browser tests. Install Chromium with `npx playwright install --with-deps chromium`. These checks never use an inherited production DATABASE_URL; all integration fixtures use a disposable replica set.

Browser checks exercise invoice paging/search and route transitions, creating a project and logging time, publishing a PDF template, and desktop/mobile rendering of the warehouse, cost review, accountant and document workspaces. API tests separately cover permissions, concurrent writes, period closing, OCR retries, immutable PDF versions and purchase document immutability. This is automated regression coverage, not a claim that every possible user action was tested.

## Queues and errors

Existing durable KSeF, OCR, webhook and reminder queues remain authoritative. Netlify now schedules the KSeF worker every minute, alongside the existing other workers. Configure HTTPS APP_URL and CRON_SECRET. An uncertain KSeF result remains `verify_needed`; do not resend it without reconciliation. On other hosts, schedule POST /api/ksef/queue/process with the configured bearer secret. Inspect company queue health in the integration panel.

Unexpected API exceptions emit JSON stderr events containing `application_error`, timestamp, incident and stack fingerprint; raw exceptions, financial payloads and credentials are excluded. HTTP 500 responses include the incident reference. Configure the hosting log sink to alert on these events and cron failures; no paid monitoring provider or outbound notifications are enabled by code alone. The application error boundary provides a retry action.

## Status reconciliation and offline preparation

The KSeF panel offers an operator-triggered status check for uncertain tasks. The endpoint requires `canSendKsef`, uses an active session scoped to the invoice owner, seller NIP and environment, and finalizes a task only for an MF acceptance with a KSeF number or an explicit rejection. Pending results never initiate a second send. Demo reports only locally stored state.

Offline preparation records a selected reason and manually confirmed upload deadline, surfaced in the owner health panel. Save the document as a draft, then use **Wystaw offline z Kodem II** on its detail page. Issuance checks an active KSeF session, retrieves the certificate from MF to confirm its `Offline` type and exact fingerprint, signs the official QR II URL, persists the exact FA(3) XML and both QR URLs atomically, and locks the issued document against content edits. PDF and email are unavailable for an unsigned offline draft. The queue and direct send use that same XML with `offlineMode: true`; an uncertain result still requires reconciliation. KOD I hashes exact stored XML bytes; old historical PDF versions remain immutable and should be audited if they contain former generated QR values.

Configure `KSEF_OFFLINE_SIGNERS_JSON` in the hosting secret manager as a JSON object keyed by the company's MongoDB ID: `{ "companyId": { "environment": "test", "certificateBase64": "<DER Base64 from MF>", "privateKeyPem": "<matching PEM private key>" } }`. Use `production` only with a production certificate and matching KSeF company settings. Restrict access to this secret; never add the key to Git, browser forms or logs. A configured signer and a live, company-scoped KSeF session are required for each issuance, so installing code alone does not activate offline signing. The operator must still confirm the applicable offline mode and upload deadline against MF announcements. No real certificate was available for an end-to-end MF test.

Contractor history loads 20 documents at a time on demand; totals and balances are aggregated in MongoDB for the selected company and currency. The compact CRM card uses server totals and displays PLN sums only instead of mixing currencies. Invoice form validation points to the relevant field and surfaces structured API field errors.

## Encrypted backup and isolated restore

Use a replica set and a read-capable backup identity. Store BACKUP_DATABASE_URL and BACKUP_KEY (64 hex characters, separately backed up) in an operator-owned secret file, never in Git. `node scripts/backup/run.mjs create /secure/path/name.enc` uses a consistent MongoDB snapshot transaction, BSON-preserving canonical EJSON, gzip and authenticated AES-256-GCM. Collection options and indexes are archived; unsupported views/capped/time-series collections abort. Schema changes and snapshot/transaction limits abort the run instead of publishing a partial archive. For large databases exceeding the transaction lifetime, use managed MongoDB snapshots/PITR instead of increasing limits blindly. The archive is published atomically without overwriting existing files.

Restore: set RESTORE_DATABASE_URL to a **new empty isolated database**, then run `node scripts/backup/run.mjs restore /secure/path/name.enc exact_database_name`. Integrity and record counts are validated before connecting to the restore target. No existing data is dropped. Interrupted restores leave a partial target; inspect and choose a new database for a retry. Test in an isolated network because restored sessions, integration secrets and pending jobs are live data. Do not run application workers against the restored copy. Preserve the MFA and webhook encryption keys separately.

`deploy/backup/fakturo-backup.service` and `.timer` provide an optional daily systemd schedule. Provision a dedicated fakturo-backup user, /opt/fakturo runtime, /etc/fakturo/backup.env (0600) and /var/lib/fakturo-backups (0700, owned by that user). Adjust the node path to the deployment runtime. Enable only after a manual backup and isolated restore succeed. Monitor the unit exit code and archive freshness. Copy encrypted backups to independently protected off-host storage; choose retention with the operator. The repository does not invent storage credentials, delete old backups, enable the production schedule or claim production backups are active.

The automated drill checks exact BSON values and indexes, empty collections, wrong keys, damaged files and refusal to overwrite nonempty targets. It uses synthetic data only.

## Invoice list

The invoice screen (including mobile document cards) and command palette query /api/invoices/search with company scope, literal search, server filters, totals and 30-row keyset pages. Page selections reset on filter/company/page changes. A lightweight /api/data?invoiceMode=list omits invoice bodies for screens with dedicated data endpoints. Invoice editing, advances, recurring templates, reminders, finance/calendar and company settings still load full invoice state because they calculate from it; other screens use list mode. Their migration to server aggregates remains a separate performance limitation. New indexes are migration 012-invoice-search, reversible without deleting documents.

The contractor page includes a collapsed CSV wizard with delimiter detection, column mapping, complete scrollable preview, NIP validation and duplicate detection. It imports at most 200 rows into the selected company. The server validates the mapped rows again, rechecks `canIssueInvoices`, and serializes competing imports within a transaction. Duplicate and invalid rows are skipped and counted; successful writes are audited. Existing contractor data is never overwritten.

Saved invoice filters are collapsed by default. Batch actions apply only to selected rows on the current 30-row page. Purchase approvals continue through the cost workflow guard. Batch settlement requires `canRecordPayments`, a fresh invoice version and an open accounting period; one transaction records the remaining balance as a payment for each eligible sales invoice and updates its status, or rolls back the entire batch. Failed actions do not show a success message. Bulk KSeF dispatch counts queued transmissions as success and does not select drafts or already pending transmissions.

Warehouse cancellation reverses historical movement value and rejects impossible negative/reserved states. It never silently substitutes today's average purchase price. Later movements may need resolving before a historical receipt can be cancelled.

## Compact overview and reporting

The dashboard and analytics use `GET /api/overview?companyId=...&months=6|12|24` instead of transferring all invoice bodies. The endpoint rechecks company membership and permissions, uses a company-scoped MongoDB aggregation to compute counts, sums, VAT and top clients inside the database and returns at most eight invoice actions, five recent documents and bounded queue metadata. Sales exclude drafts and proformas, and currencies are never combined. Every read reflects committed invoice changes; no separate invalidation process is required. Charts span the selected 6, 12 or 24 months while headline totals cover all issued invoices. Other legacy forms and accounting screens still request complete invoice data.

The dashboard only shows a short action list and one month chart; further details are expandable or link directly to the review, period or invoice. The KSeF screen adds the public MF Latarnia status and notices, a company-scoped queue summary and public X.509 validity dates. Details are collapsed initially. The service only stores certificate dates and SHA-256 fingerprint; it does not store uploaded public files, accept P12/PFX private-key bundles, authenticate with the certificate, or confirm certificate authorization in MF. A missing certificate means no certificate metadata was supplied, not that the KSeF token is absent. MF API failures display an unknown status. The health screen continues to display queue history and retry counts. An uncertain result is never automatically retried from these screens. Raw worker errors are not copied into overview responses.

## Operator checks

The operator probe can POST its failure JSON to an operator-controlled HTTPS endpoint when `MONITOR_ALERT_WEBHOOK_URL` is configured. Delivery failure is logged without the endpoint or its credentials; the probe still exits nonzero. Configure alert throttling and a destination that accepts this JSON on the monitoring side. The owner health view shows compact queue, webhook and offline deadline warnings; archive freshness remains visible only to the external probe.

`scripts/ops/check-health.mjs` checks the public HTTPS `/api/health` response and the age and size of encrypted `.enc` files in a local backup directory. It exits nonzero and writes one JSON event on failure, without printing database credentials. Configure `MONITOR_HEALTH_URL=https://your-host/api/health`, `MONITOR_BACKUP_DIR=/var/lib/fakturo-backups` and optionally `MONITOR_BACKUP_MAX_AGE_HOURS=36` in `/etc/fakturo/monitor.env` with mode 0600. Install `deploy/backup/fakturo-health.service` and `.timer` into systemd, adjust the Node/runtime paths, manually run the check after a backup, then enable the timer. Connect failing unit alerts to the hosting/operator monitoring service and verify an intentional failed check raises an alert. On Netlify or another platform, run the script from a trusted external host with access to the backup directory; the repository cannot read that host's archives itself.

Copy encrypted archives to independently protected off-host storage and configure retention and access with the operator. Neither the timer nor the off-host copy is active merely because these files are committed. An archive freshness check cannot substitute for periodic isolated restore drills, which the earlier section describes.

For an operator-selected off-host storage, `deploy/backup/fakturo-backup-copy.service` and `.timer` invoke `scripts/ops/copy-backups.mjs` after the daily backup. Install rclone and its protected remote config on the backup host, set `BACKUP_COPY_SOURCE=/var/lib/fakturo-backups` and `BACKUP_COPY_TARGET=remote:private/fakturo` in `/etc/fakturo/backup-copy.env` (0600), and run a manual transfer plus an independent read and restore before enabling the timer. The transfer only copies encrypted `.enc` archives with `--immutable` and does not delete local or remote files. Configure off-host age/availability alerts and retention through the chosen storage service; local freshness alone does not prove that an off-host copy exists. No remote, credentials, timer or retention policy is enabled by the repository.

The operator probe also checks the NBP exchange-rate table and reachability of the KSeF test gateway. Set `MONITOR_KSEF_URL` to the matching official `https://api-test.ksef.mf.gov.pl/v2`, `https://api-demo.ksef.mf.gov.pl/v2` or `https://api.ksef.mf.gov.pl/v2` endpoint if needed. A gateway response confirms only connectivity, not authenticated FA(3) submission, acceptance or UPO. Verify those separately in the target environment. The script must run on an external host to detect an application outage; it is not activated by a Netlify deploy.

The external probe now requires `MONITOR_BACKUP_COPY_TARGET=remote:private/fakturo` (the rclone directory holding encrypted copies) in `/etc/fakturo/monitor.env`. It runs `rclone lsjson` and fails if no nonempty encrypted archive was copied within `MONITOR_BACKUP_MAX_AGE_HOURS`. Configure a separate rclone read-only remote for the monitor; monitor failures should reach the independent alert destination. This proves only freshness and size metadata; periodically restore an archive from the offsite copy to an isolated database. On Netlify, run this probe on a separate host, since Netlify Functions cannot inspect the backup host's filesystem or rclone configuration.

## KSeF MF test smoke after deployment

On the deployed HTTPS test environment, prepare a disposable seller and buyer and one valid draft invoice. Save its company and invoice IDs in the operator environment. Run `node scripts/ops/ksef-smoke.mjs` with `KSEF_SMOKE_BASE_URL`, `KSEF_SMOKE_COOKIE` (an authenticated test account cookie), `KSEF_SMOKE_COMPANY_ID`, `KSEF_SMOKE_INVOICE_ID` and `KSEF_SMOKE_SEND=test`. The script checks the actual MF test gateway and token authentication, submits that one invoice once, polls its status and requires a KSeF number and UPO. It never switches to production or retries a submission with an uncertain result. Keep the cookie outside Git and shell history. A gateway ping alone is insufficient. Separately exercise rejection and ambiguous-result reconciliation in the MF test environment; do not resend an uncertain invoice. No real MF token, target deployment or offsite backup host is available in this repository, so this test cannot be claimed as executed from a code build.
